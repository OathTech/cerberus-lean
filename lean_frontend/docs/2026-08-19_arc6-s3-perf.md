## What changed

### 1. LemLib `Fmap` (lem-lean `lean-lib/`, commit `40d063e`)

`Fmap α β := List (α × β)` (assoc list; `fmapAdd` = cons + full
BEq-filter O(n), `fmapLookupBy` = linear comparator scan O(n) — S0's
dominant exec cost at every generated lem `map` seam) is replaced by a
two-index representation:

- `bySeq : Std.TreeMap Nat (α × β)` — the ORDER SPINE. `fmapElements`
  enumerates seq-descending = exactly the newest-first list the old cons
  spine exposed, so every fold order (`Map_extra.fold` = setFold =
  `List.foldr`, i.e. oldest-first application; `toSet`/`toList`/
  `domainBy`/`rangeBy`) is preserved bit-for-bit.
- `byKey : Std.TreeMap α (List (Nat × α × β)) cmp` — the lookup index,
  keyed by the lem `mapKeyCompare` comparator CAPTURED at first insert
  (`Fmap.empty` is a nullary constructor: `lean_box(0)` remains a valid
  empty map — the ABI cerberus `native/tags.c` relies on). A bucket is
  the comparator-EQ class, seq-descending, deduplicated by `BEq` only —
  reproducing old `fmapAdd` exactly where BEq is strictly finer than the
  comparator (`sym`: symbol_description-sensitive derived BEq vs
  digest+num `symbol_compare`; `identifier`: loc-sensitive derived BEq
  vs string-only compare). Lookup = bucket head (= the old head-first
  scan's first match); delete removes the whole bucket (= the old
  remove-all-comparator-EQ filter).

**Fold-order decision [AGENT:S3]:** the swap preserves the CURRENT Lean
enumeration order (insertion-ordered, newest-first spine; update moves
the key to newest) — NOT OCaml's key order. S0 noted key-ordered folds
would be a parity improvement, but the S3 bar is ZERO movement and
improvements are also movement; adopting oracle fold order is left as a
priced follow-up (it would need a fresh differential baseline pass).

`library/map.lem` changes are lean-scoped declares only (other backends
untouched): `insert`/`(union)` route through new `insertBy`/`unionBy`
vals carrying `mapKeyCompare` (the existing lookupBy/deleteBy pattern),
and `toSet` maps to `fmapElements` instead of `id`. No lean-backend
(`src/lean_backend.ml`) changes.

**Soundness assumptions** (stated in LemLib.lean, checked against the
generated frontier):
1. Per map value, all comparator-taking ops receive the same comparator.
   lem inlines the static `mapKeyCompare` instance per key TYPE; sym maps
   uniformly use `ordCompare` (= `symbol_compare`), the only custom
   comparators in the frontier (Core_linking / Cabs_to_ail_effect
   identifier-by-string) coincide with identifier's lem SetType instance
   (string-only). Ops use the CAPTURED comparator on the tree.
2. BEq-equal ⟹ comparator-EQ (BEq at every `fmapAddBy` site is
   structural-derived or the Map.lean bridge; comparators are reflexive
   functions of the key value).
3. Comparators are lawful total preorders (`Std.TransCmp` after
   lifting) — all `mapKeyCompare` instances are lexicographic orders.

### 2. Equivalence obligations (D7) — `lean-lib/LemLibTest.lean`

Built by default (`lake build` runs it; part of the lem gate).

PROVED (kernel-checked; axiom cone = propext/Classical.choice/Quot.sound
only):

  new and retired implementations return equal lookup results at every

### 3. CerbMem (cerberus side, hand-written)

- `bytemap : List (Int × AbsByte)` → `Std.TreeMap Int AbsByte` and
  `allocations : List (Int × Allocation)` → `Std.TreeMap Int Allocation`
  (OCaml at the same seams: `IntMap = Map.Make(Z)`, impl_mem.ml:93).
  Both are order-UNOBSERVED in CerbMem (never folded/enumerated) and
  have unique keys by construction (fresh ids; per-address bytes), so
  `get?`/`insert`/`erase`/`map` return exactly what
  `find?`/`cons+filter`/`filter`/`map` did. `writeBytesTo` no longer
  filters the whole bytemap per store; `readBytesFrom` is O(log n)/byte.
- `deadAllocations` stays a List — OCaml's own `List.mem` seam
  (impl_mem.ml:667, 781, 809) is the oracle's asymptotics; kept faithful.
- Sites that consumed the ambient tag map as a raw list (offsetsof/
  find? in CerbMem, `alignof_ty` in CerberusImpl, `offsetofIval`'s lem
  target_rep boundary, `Main.lean` libc assembly and signature pp,
  EffectsProofTest's literal map) now go through `fmapElements` /
  `fmapAddBy`/`fmapOfSpine` with the SAME comparators generated code
  uses (`symbol_compare`, identifier-by-string,
  `implementation_constant_compare`) and the same scan predicates —
  bit-identical results by construction (`fmapOfSpine` preserves the
  built list as the exact enumeration spine).

the 339-pt battery slice still timed out — the accumulated dead
allocations made CerbMem's per-store whole-bytemap filter the binding
term at 339 points (S0's "secondary" seam). Both swaps together meet
the bar with ~3× headroom.

## Stack ceiling re-probe (Task 5; S0 register item — NOT fixed here)

Post-fix the ceiling is now cleanly separated from map costs. Probe:
`for (i = 0; i < N; i++) b = 1;` single-trace:

- N ≤ 1280: normal, ~0.3 s, correct verdict.
- N ≥ 1408 (1408/1536/2048/4096/8192 probed, 2 runs each): ALWAYS fails,
  BIMODALLY — either quiet death at ~1.35 s wall (empty stdout, observed
  process exit 0 through `timeout`; a differential harness still sees it
  loudly as a missing verdict) or a hang until timeout. Mode varies run
  to run at the same N (ASLR-adjacent stack-guard behavior suspected;
  S0 saw SIGABRT for the same class).
- Not corpus-binding: the full battery (339-pt slices), minimal,
  coverage, debug, libc_exec, uri, multi_tu all pass; no standing corpus
  approaches ~1.4k same-loop iterations.
- Register: onset ~1.4k plain-loop iterations; the quiet-death exit-0
  mode is the ugliest facet (fail-loud only via missing output). Fix
  belongs to a dedicated runner-recursion slice, not S3.
