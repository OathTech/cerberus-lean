## 7. THE PARKED CONFLICT — libc-mode surface (STOP-ITEM for the operator/coordinator)

Two S1 bars could not be reconciled by this worker without reversing a
D1 ruling, and the underlying measurements changed the picture. PARKED
per park-don't-improvise; no libc/uri baseline was touched.

**Measurements (the new facts):**

1. `.co` loading is MARSHALLED (`main.ml:26-27 read_core_object`) — it
   draws nothing. The S0 "libc margin ≈ 11,250" was WRONG (corrected
   by addendum): **the C-TU margin in libc mode is the same 483**.
2. `libc_prep.sh --jsons` (the fork's own libc metadata pipeline) runs
   `--nolibc --cabs-json` over the 12 libc source TUs; under the floor
   4 of 12 REFUSE: stdio (hwm 856), stdlib (673), internal (682),
   vfscanf (521). Verbatim first failure:
   `libc_prep: ERROR: cabs-json failed for stdio.c` →
   `test_libc_exec.sh` FAILS at prep (the 7 lane programs themselves
   all pass the floor and agree — §5).
3. The un-floored fork elaboration of those TUs carries LIVE
   collisions (plant-binary duplicate scans, digest-aware):
   stdio **214**, stdlib **58**, internal **106** (e.g.
   `DUP num=526: ['__uflow', 'ret_526']` — a real libc function
   symbol equal to a return label), vfscanf 0 (supply-only overflow).
   **The pinned libc.co was BUILT from these TUs by the un-floored
   oracle — the fork's libc Core objects have been F-D-exposed since
   the desugar threading.** Any libc.co REBUILD under the floor
   (runtime/libc/dune elaborates the same sources) will refuse.
4. `test_libxml2_uri.sh` ORACLE_LIBC lane: uri.c itself has hwm 1798 →
   backward-floor (verbatim: `[oracle+libc] exit=70` →
   `FAIL: GATE: ORACLE_LIBC expected exit 0, got 70`). uri.c's
   un-floored elaboration carries **252 live collisions** including
   `__xmlLastError`/`__xmlGenericError`/`__xmlStructuredError` vs
   SD_None temporaries. The 16/16 uri baseline has been computed over
   a collision-exposed oracle elaboration all along (its agreement
   with Lean was evidence the collisions were benign IN THAT LAYOUT —
   the coincidentally-correct class at gate scale).

**Why parked:** charter S1 bar (e)/success condition 2 name uri/libc
"zero movement", while D1 ruled "--cabs-json floors too" and the floor
semantics D1 approved are exactly what refuses these TUs. Honest
flooring and libc/uri-lane green are IRRECONCILABLE without either a
scoped exemption (weakens the floor where it demonstrably found live
exposure) or renumbering (the charter's deferred route).

**Options priced for the ruling:**
- (A) Status quo of this branch: floor uniform; libc_exec + uri lanes
  RED (honestly); libc.co rebuild blocked; all other lanes green.
- (B) Cabs-json-export exemption (driver-level, explicit): restores
  libc_prep's 12 metadata JSONs (Cabs bytes are desugar-independent —
  collisions cannot corrupt the JSON, only produce wrong hard-error
  verdicts, a documented residual). Does NOT restore the uri lane
  (exec path) nor libc.co rebuilds (elaboration path). Reverses a D1
  sentence — needs an explicit ruling.
- (C) Grandfather the PINNED artifacts (libc.co + uri baseline) with
  register findings recording their exposure, keep using them
  read-only (drift-checked), accept RED on rebuild paths until
  renumbering. Combinable with (B) to re-green test_libc_exec while
  leaving the uri ORACLE_LIBC lane red or re-scoped.
- (D) Pull renumbering forward (the charter's replan bullet): the
  measurements now show beyond-margin TUs are not tail cases but the
  fork's own libc and any ~500-identifier TU — the strongest argument
  yet that the id-space split needs the real fix.
