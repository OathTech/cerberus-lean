## 1. Facts (verified by the orchestrator 2026-09-18; cite, do not re-derive; errata to the record)

**Transparency of `panic!`.** Lean's `panic!` is a transparent definition returning `default`: the orchestrator's probe at `e64819de7` — `example : CerbMem.combineProv (.Prov_symbolic 0) .Prov_none = .Prov_none := rfl` and `example : CerbMem.bytesToInt [] false = none := rfl` — both compile (the consumer's `probes/2026-09-18_hidden_panic_default.lean` shows the same). So at every seam `panic!` the KERNEL model continues with a default value where the binary aborts (`LEAN_ABORT_ON_PANIC=1`, `Main.lean`) and the oracle raises: a downstream theorem can be proved through such an arm.

**The library's failure leaves are already opaque.** `lem-lean/lean-lib/LemLib.lean:167-178`: `@[never_extract] private unsafe def failwithIImpl {α} [Inhabited α] (msg : String) : α := panic! msg` and `@[implemented_by failwithIImpl, never_extract] opaque failwithI {α : Type} [Inhabited α] (msg : String) : α := default` — no equations for the kernel; at runtime "panics with the message, byte-identical behavior to the retired legacy failwith". `fuelExhaustedWith` likewise. The generated model (219 modules) uses only these. The runtime difference between `panic! msg` at a seam and `failwithI msg` is the PANIC SITE printed before the message (`PANIC at CerbMem.f CerbMem.lean:L:C: msg` → `PANIC at LemLib.failwithIImpl LemLib:168:2: msg`); the message text is unchanged.
