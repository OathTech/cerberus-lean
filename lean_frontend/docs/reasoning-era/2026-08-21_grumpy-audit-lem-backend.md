# Grumpy-Professor Audit: the lem Lean backend + LemLib runtime

Date: 2026-08-21. Auditor persona: grumpy PL professor, publication-gate review.
Target: `lem-lean/src/lean_backend.ml` (5,082 lines, entirely this project's work,
2026-03-06 → arc 10), its hooks (`process_file.ml`, `backend_common.ml`,
`target_trans.ml`, `typed_ast.ml`, `ast.ml`, `parser.mly`), and the runtime
`lem-lean/lean-lib/` (`LemLib.lean` hand-written, 29/30 `LemLib/*.lean` generated,
`LemLibTest.lean`). Comparison baseline: `src/backend.ml` (4,167 lines, four targets),
`src/coq_backend.ml` (1,602 lines), `src/backend_common.ml` — read and internalized
before judging. Operator directive mid-audit: severity weights toward SEMANTIC
fragility — constructions whose correctness rests on accidents rather than stated,
checked invariants. Read-only audit; no fixes; recommendations only.

Baseline facts the grading rests on:

- Upstream house style: per-target token modules (`module type Target`) plugged into
  one shared traversal (`Backend.Make`), everything in the `Output.t` combinator
  algebra (kwd/id/meta/ws) preserving lex_skips; effect-free emission; errors through
  `Reporting_basic` with locations; the language grammar normatively defined in
  `language/lem.ott`, from which `src/ast.ml` is generated (`language/Makefile:10-13`,
  which even does `chmod a-w ../src/ast.ml`).
- `coq_backend.ml` is the closest structural precedent: a separate file, an
  `CoqBackendAux` functor re-instantiated per definition inside a `List.fold_right`
  (coq_backend.ml:1560-1577). Our backend copies that skeleton faithfully
  (lean_backend.ml:4883-4917) — the fold_right and per-def functor are INHERITED,
  not invented. Upstream gets away with fold_right because upstream emission is
  pure. Ours is not. That asymmetry generates half the register below.

### GRAVE

**G1 | GRAVE | THEORY | lean_backend.ml:4295-4371, 4376-4465; LemLib.lean:92-93;
LemLib/Basic_classes.lean:50**
The correctness of every generated comparison rests on an instance-priority lattice
smeared across three artifacts — derived real instances at default priority
(:4349-4358), open-tyvar failwithI fallbacks at `priority := 50` (:4361-4371),
residuals at `priority := low`, LemLib's generic default-priority bridges, and the
low-priority default `Eq0` in Basic_classes — with the tie-breaker explicitly relying
on "equal priority resolves newest-declaration-first" (:4345-4348), i.e. an
elaboration-order accident, and with the failure mode of a lost race being not a
compile error but a RUNTIME failwithI panic (or, pre-arc-10, a silently wrong
comparison); nowhere is the lattice stated in one place, and nothing — no generated
probe, no test — checks that the intended instance actually wins at each generated
type. This is the F-D family's backend-side sibling the operator asked me to find:
the comment at :4340-4348 candidly admits the generic bridges "would otherwise
shadow a low-priority real instance and complete through the unconstrained
failwithI fallback" — meaning the author has already once been bitten by exactly
this race and responded by adjusting one priority rather than by writing down and
checking the order. Remedy: single normative priority table (design note + LemLib
comment), plus a generated-or-hand-written resolution probe per instance class that
fails the build when the wrong instance is selected. **M**

**G2 | GRAVE | UPSTREAM | src/ast.ml (header: "generated by Ott 0.31 from:
lem.ott"), language/lem.ott, language/Makefile:10-13, parser.mly:1029**
The fork hand-edited the Ott-GENERATED `ast.ml` (Decl_fuel_decl, Decl_reader_decl,
Decl_reader_seed_decl, Decl_ground_rep_decl, Decl_effectful_decl at ast.ml:508-513)
without touching `language/lem.ott` — the file upstream write-protects precisely to
prevent this — so the normative grammar no longer describes the language, and
running the documented build rule (`ott ... -o ../src/ast.ml lem.ott`) would delete
the fork's declare forms and break the build; the lean TARGET was added to the ott
source (lem.ott:698), so the discipline was known and then abandoned. The Sewell
lineage treats the ott spec as the definition; this alone blocks upstreaming.
Remedy: add the declare productions to lem.ott, regenerate, diff-verify. **M**

**G3 | GRAVE | PRACTICE | lean_backend.ml:62-231, 756-767, 4931-4934**
The backend is a hidden global state machine: some two dozen module-level mutable
refs (`lean_auxiliary_opens`, `lean_namespace_stack`, `lean_mutual_records`,
`lean_collected_imports`, `lean_local_modules`, `lean_deferred_opens`,
`lean_current_module_name`, `lean_inhabited_census`, `lean_inhabited_tier2_plans`,
`lean_prop_equality`, `lean_pending_abbrevs`, `lean_indreln_params`,
`lean_reader_lifted`, `lean_reader_binder`, `lean_inhabited_binder`,
`lean_fuel_emit`, `lean_fuel_workers`, `lean_reader_seed_param`,
`lean_failwith_threaded`, `lean_rendering_comment`, `fresh_name_counter`,
`lean_reader_params_cache`, plus `Backend_common.on_cr_simple_applied` and the
`process_file.ml` module-name side channel), some reset per file, some per
invocation, and one (`lean_mutual_records`, :4933-4934) deliberately NEVER reset —
process-lifetime accumulation keyed by nothing; correctness of the census/threading
state rests on unasserted invariants ("modules are processed in dependency order",
"one lem invocation") stated only in comments, and the whole thing is non-reentrant
where every other backend in the tree is a pure function from typed AST to rope.
Each individual ref has a save/restore discipline (`Fun.protect`, consistently —
credit), but twenty disciplined mutable cells are still a state machine nobody can
hold in their head. Remedy: one explicit analysis-state record (or state module)
with a stated invariant per field, threaded or passed via the functor argument;
restore effect-free emission. **L**

**G4 | GRAVE | LIB | LemLib.lean:258-281 (setAdd, setFromList, setMemberBy,
setEqualBy) vs 379-403 (Fmap bucket rationale)**
The Set layer mixes two equalities — `setAdd`/`setFromList` deduplicate by `BEq`
while `setMemberBy`/`setUnionBy`/`setEqualBy` use the comparator — so with a `BEq`
strictly finer than the comparator (the exact cerberus `sym` situation the Fmap
section documents at :385-390 as load-bearing!), a set can hold comparator-EQ,
BEq-distinct duplicates, and `setEqualBy`'s `s1.length == s2.length` guard then
denies extensional equality of equal sets: the very hazard the Fmap rewrite solved
with buckets survives, unacknowledged, one page up in the same file. Semantic
divergence from OCaml lem's comparator-keyed psets is possible without any
differential test knowing which seam to poke. Remedy: comparator-only set
operations (or bucket-style coherence), plus a Set-section soundness note matching
the Fmap section's standard, plus an adversarial-key property test like the Fmap
one. **M**

**G5 | GRAVE | THEORY | backend_common.ml:258-266; lean_backend.ml:324-337,
5048-5058**
"Is this a library module?" is answered by a proxy — "does it carry a `{coq}`
rename?" — implemented twice (once in backend_common's name transformation, once in
the backend's transitive-opens scan), so any user `.lem` module that happens to
declare a Coq rename is silently reclassified as a LemLib library module: different
namespace (`Lem_*` wrapper), different import/open scheme, different opaque-type
filtering (`is_library_module` gates Te_opaque skipping at :573, 4811-4812) — a
semantic change triggered by an unrelated, perfectly legal user declaration. This
is correct only for today's corpus shapes; the operator's elevation rule applies
squarely. Remedy: an explicit library marker (a declare, or a path-based flag
threaded from the CLI), one implementation. **M**

### SERIOUS

**S1 | SERIOUS | THEORY | lean_backend.ml:64-80, 1111-1132, 3281-3288**
The keyword-escaping scheme is a hand-grown blocklist that conflates three distinct
name classes — true Lean keywords (`match`, `do`), prelude CONSTRUCTORS (`none`,
`some`, `true`, `false`), and plain prelude functions (`pure`, `get`, `set`,
`panic`) — and its one mechanism, guillemets, is lexically inert for the class that
matters most: `«none»` in pattern position still resolves to `Option.none`, so a
Lem binder named `none` matched against an Option scrutinee would silently become a
constructor pattern (a capture bug, the worst kind: no error, wrong semantics),
while escaping `pure` achieves precisely nothing (`«pure» ≡ pure`); no in-repo
probe pins either behavior. To be fair: the Lean entry in the avoid machinery
(`target_trans.ml:488`) mirrors Coq's exactly, so blocklist-in-backend matches house
practice — but house practice does not have Lean's binder-vs-constructor pattern
ambiguity to contend with. Remedy: classify the list; route true collisions through
the rename/avoid machinery (which the fork already receives as `A.avoid`) instead of
quoting; add a probe for the `none`-binder case. **M**

**S2 | SERIOUS | THEORY | lean_backend.ml:1160-1165, 194-217, 2535-2557,
2766-2775, 4604-4614**
Every synthesized name — `lemFuel`, `<f>_lemFuel`, `_lemReader_<name>`,
`x<n>`/`y<n>`, `cmpx_`/`cmpy_`, `<T>.beq_derived`, `<T>.<kind>_deriv_aux<n>`,
`default_inhabited`, `ctor_rank_ocaml` — is chosen by convention with no stated
reserved-namespace contract and no collision check, bypassing lem's own
capture-avoidance machinery; concretely, a user variable named `lemFuel` inside a
fuel'd body shadows the fuel binder, and the self-call rewrite `worker lemFuel`
(:2774) then silently passes the USER's value as fuel — if it is a Nat, no error,
wrong recursion budget. The `cmpx_`-style trailing-underscore convention shows the
author knows the hazard; the discipline is just not uniform or documented. Where we
synthesize binders we are doing substitution, and substitution without a
freshness argument is not PL theory, it is luck. Remedy: one documented reserved
prefix (e.g. `_lem`), applied to every synthesized binder, plus a generation-time
collision check against the def's bound names. **M**

**S3 | SERIOUS | THEORY | lean_backend.ml:123-138 (lean_builtin_inhabited_entries)**
The Inhabited derivability analysis closes its world with a default: any type head
absent from the census "defaults to [[]]: assume an unconditional instance exists"
— an optimistic assumption whose failure is deferred to a Lean elaboration error
inside GENERATED code, far from the .lem source, in direct tension with the
fail-closed-at-generation-time discipline the same file enforces everywhere else
(and advertises in its own header, :20-30). The comment honestly labels the
trade-off ("visible, never a hidden inconsistency") — but "loud, elsewhere, later"
is the diagnosis-cost profile this project's doctrine exists to avoid. Remedy:
enumerate the known-instance heads explicitly (the set is small) and make unknown
heads a generation-time warning-or-error with the standard escape hatches. **S**

**S4 | SERIOUS | THEORY | lean_backend.ml:241-282 (reader), 547-602 (inhabited),
905-1001 (threading), 4549-4560 (comparison solve)**
Four fixpoint computations, none stated as such: no lattice, no monotonicity lemma,
no termination argument beyond the word "monotone" in a comment — e.g. the
threading fixpoint's termination actually depends on the un-stated fact that a
callee's threaded position set can only grow (positions are recomputed from demands
that are unions over a growing threaded map; if that ever became non-monotone the
`while !changed` loop at :944-980 could oscillate), and the whole pass battery
additionally depends on lem's module dependency order and per-file declaration
order (stated in comments at :99-103, 1003-1018, never asserted). The analyses are,
as far as I can verify, CORRECT — the derivation rules (tier split, pending-path
skipping, phantom-tyvar guard) even mirror a real design note
(doc/notes/2026-08-20_arc8-inhabited-threading-design.md, cited by rule number,
which is more than most industrial compilers manage) — but the side conditions are
folklore-in-comments, not theorems-in-comments: nothing states WHY each worklist
terminates or why the pre-pass/emission re-run is confluent beyond "all the passes
are monotone" (:1016). Remedy: a paragraph per pass — domain, order, monotone
step, bound — plus cheap `assert`-style checks of the order invariants. **M**

**S5 | SERIOUS | PRACTICE | lean_backend.ml:241, 547, 905, 4940-4969; plus
add_def_entities per def at :4885**
The pre-pass sediment: five-plus independent AST walks per module (reader fixpoint,
Inhabited census, threading fixpoint, local-module pre-collection, mutual-record
pre-collection — each with its own recursion boilerplate over `Module`/`Val_def`),
each carrying its own copy of the same apology ("emission walks definitions with
fold_right — side effects run last-to-first — see the lean_reader_prepass /
lean_mutual_records precedent", :139-144, 537-546, 4936-4953). When the same
workaround rationale is pasted five times, the object of the workaround — a
side-effecting emission over an upstream-pure fold_right — is the defect, and the
passes are its symptoms. The walks share no traversal infrastructure and will
quintuplicate again at the next analysis. Remedy: either make emission effect-free
(G3) so order stops mattering, or one generic def-tree fold that all analyses
instantiate. **L**

**S6 | SERIOUS | PRACTICE | lean_backend.ml, 33 of 43 `err_general` sites**
Thirty-three of the backend's forty-three fail-closed errors are raised at
`Ast.Unknown` — including every fuel/reader/seed combination error (:2095-2174) and
the instance-method reader guard — so the user of this famously fail-closed backend
is told precisely WHAT is unsupported and not WHERE it is, in a codebase whose
upstream threads locations through every error path (`Reporting_basic` exists for
exactly this). Locations are available at nearly all these sites (the funcl carries
one; the def carries `l`). Fail-closed but location-blind is half a diagnostic.
Remedy: plumb the enclosing def's `Ast.l` into the guard raises. **S**

**S7 | SERIOUS | STYLE | lean_backend.ml:1085 (from_string = meta_utf8),
4500-4503 (lean_output_str), 4604-4799 (sprintf generator)**
The backend nominally uses the `Output.t` algebra but has abandoned its point:
everything — keywords, identifiers, structure — is emitted as `meta_utf8` strings
(so the `need_space`/token-class machinery it dutifully defines at :1065-1083 is
largely vestigial), and the arc-10 derived-comparison generator is built entirely
from `Printf.sprintf` with `lean_output_str` ROUND-TRIPPING Output → rope → string
→ Output to render types into string templates. The other backends never leave the
combinator algebra; ours treats it as a string buffer with extra steps. Remedy:
pick one: either commit to the Output discipline (kwd/id classification, one
rendering path) or honestly define a small string-emission layer — not both. **M**

**S8 | SERIOUS | THEORY | lean_backend.ml:2673-2676**
The reader-application rewrite replaces the ENTIRE application spine with the
injected parameter on the assumption "the only argument is unit" — unchecked; a
reader constant of arity beyond `unit -> T` applied to extra arguments would have
those arguments silently dropped from the emission, recovered only by a downstream
Lean type error whose message mentions none of this. One `if List.length args <> 1
then err` is all it costs to make the assumption a theorem. Remedy: guard. **S**

**S9 | SERIOUS | PRACTICE | lean_backend.ml:314-322 (check_beq_target_rep)**
Recognizing the BEq operators by matching `Ident.to_string` against `"=="` OR
`" =="` — the second variant existing because lex_skips leak into the rendered
ident — is accident-tolerant string matching: semantics (propositional-equality
rewriting in indreln antecedents) keyed off a whitespace artifact that any upstream
change to `Ident.to_string` silently perturbs. Remedy: strip skips before
comparing, or match on the resolved constant rather than its rendering. **S**

**S10 | SERIOUS | UPSTREAM | lean_backend.ml:1197-1223 (@Class.method string
parsing), 1291-1305 (Eq0/SetType table), 1600-1624 (setElemCompare/mapKeyCompare,
lean_global_names)**
The backend hardcodes knowledge of the lem LIBRARY into the COMPILER: the class
names `Eq0`/`SetType` mapped to `BEq`/`Ord` constraints, the comparison-method
names `setElemCompare`/`mapKeyCompare`, the clash list `["max"; "min"; "compare"]`
("Review this list when upgrading the Lean toolchain"), and — worst — typeclass
constraints extracted by string-parsing `@Class.method` patterns out of
`Path.to_string` on user-written backend quotations (:1202-1213). Lem's design
puts target knowledge in library `declare`s precisely so backends stay
library-agnostic; the maintainers would reject each of these on sight. Remedy:
move the tables into library declares (a `declare {lean} class_rep`-style form if
needed); parse backend quotations structurally, not stringly. **M**

**S11 | SERIOUS | LIB | LemLib.lean:560-650 (LemRational et al.), 780-781 (THE),
347-350 (setChoose) vs 146-159 (failwithI's stated discipline)**
The library preaches opacity for failure ("an error branch is not provably equal
to any value", failwithI's docstring) and then implements a dozen failure paths
with bare `panic!` in transparent `def`s — and `panic!`'s logical value IS
`default`, so `THE p = none`, `LemRational.beq x y = false`, and
`setChoose [] = default` are all PROVABLE: any theorem whose statement reaches
these paths is quietly a theorem about arbitrary default values, exactly the
claim-hygiene failure the failwithI design was built to prevent. The two
disciplines cannot coexist in one file without a paragraph explaining which
applies where. Remedy: route library failure paths through failwithI (or opaque
wrappers), or document per-def why transparency is acceptable. **M**

**S12 | SERIOUS | LIB | LemLib.lean:632 (natSqrtAux), 821 (set_tc)**
Two `partial def`s in the hand-written runtime of a project whose standing doctrine
is that partial defs are kernel-opaque trust gaps requiring a declared boundary
entry: `set_tc` has an obvious bound (pairs are drawn from a finite square; the
length strictly grows per iteration) and `natSqrtAux`'s Newton iteration is
classically terminating — neither carries a boundary-list justification or a
TODO. Remedy: fuel-or-measure totalize both; `set_tc` is an afternoon. **S**

**S13 | SERIOUS | LIB | LemLib.lean:71-75 (Vector.slice), 903-913
(mwordConcat/mwordExtract/mwordUpdate)**
`Vector.slice` ignores its `_stop` argument, takes its RESULT LENGTH from the
expected type at the use site (an implicit `m` — semantics by elaboration
context), and pads out-of-range reads with `default` — three silent behaviors in
one two-line definition, with none of the justifying commentary its cousins get
(mwordExtract at least documents "hi is redundant... same as Isabelle's
Word.slice"); it also injects itself into core's `Vector` namespace. Remedy:

rename `_stop`, decide pad-vs-panic deliberately. **S**

**S14 | SERIOUS | PRACTICE | lean_backend.ml:1003-1031; process_file.ml:407-416**
Cross-invocation analysis reconstruction: a cerberus invocation recomputes the
LIBRARY's census/threading maps from the library .lem sources it typechecked,
trusting that this reproduces the analysis that generated the library's
`.lean` files at some earlier time with some earlier backend — nothing pins the
two (no version stamp, no signature hash in the generated files), so
backend-version skew between `make lean-libs` and a later generation run yields
callers threaded against signatures the on-disk library does not have, caught
only at Lean build with an instance-resolution error. The design note honestly
derives the recomputation ("the same analysis that emitted the library, never a
hardcoded list" — good), but "same analysis" is a claim about two points in
time. Remedy: emit an analysis fingerprint comment into generated library files
and check it (or accept and DOCUMENT the make-driven freshness assumption in the
backend, not just the build system). **M**

**S15 | SERIOUS | PRACTICE | process_file.ml:365-405; backend_common.ml:369-374**
The Lean output case diverges from its seven siblings in interface hygiene: it

**S17 | SERIOUS | THEORY | lean_backend.ml:164-166, 1782-1821, 4989-4992**
Deferred abbrevs (`lean_pending_abbrevs`) are drained at END of file, after every

## Where the code is already excellent (the professor is grumpy, not dishonest)

1. **The fail-closed error discipline is better than upstream's.** Upstream lem
   backends routinely emit known-broken output silently (the Coq backend's own
   corners; TODO-riddled cases); this backend, post arcs 8/10, refuses loudly at
   generation time, and — uniquely in my experience of reviewing student
   backends — EVERY refusal names its escape hatches ("declare {lean}
   skip_instances ... plus a hand-written instance, or a target_rep"). That is
   compiler UX upstream should adopt from us.
2. **The negative-probe suite exists.** tests/comprehensive/negative holds nine
   probes asserting that unsupported combinations FAIL (fuel×mutual×lifted,
   phantom-tyvar threading, setcomp, Type-1 comparisons...), and the panic-path
   pin in the comprehensive Makefile asserts the exact "Incomplete Pattern"
   message and the LEAN_ABORT_ON_PANIC fail-stop leg. Testing that your compiler
   rejects what it must reject is real engineering; upstream lem has nothing
   comparable.
3. **The Fmap section of LemLib.lean is model epistemics**: representation change
   with enumerated soundness assumptions, the retired implementation frozen
   verbatim as a test-only reference namespace (`LemLibLegacy`, freeze discipline
   stated and enforced by placement in LemLibTest.lean), kernel-checked lookup
   equivalence over ALL op sequences, bounded-exhaustive adversarial property
   tests for the order observables, and an honest proved/unproved split recorded
   in the header. Publish that section as-is.
4. **Mirror-citations are real**: L_undefined's renderer cites

Would it pass the grumpy professor TODAY, against "immaculate, impeccable,
exquisitely in keeping with PL theory and practice, indistinguishable from the
pre-existing backend, and absolutely aligned with the two upstreams"? No — on
three independent grounds, any one of which suffices: the grammar spec is stale
against a hand-edited generated file (G2: upstream's own build rule would destroy
the fork's language extensions); the backend's semantics lean on an instance-
priority race and a pair of equality-mixing/classification accidents (G1, G4, G5)
that violate the project's OWN no-accidents doctrine; and the mutable-global
architecture (G3) is categorically not "indistinguishable from the pre-existing
backend", whose defining property is pure token-algebra emission.

But the distance is honest and short. This is not a mess — it is a well-tested,
well-documented, aggressively fail-closed compiler whose sins are concentrated,
named, and mostly mechanical to fix: nothing in the register requires a redesign
of the analyses or the emission strategy, and the strongest parts (the negative
suite, the Fmap epistemics, the error UX) are already ABOVE the upstream bar.
One "immaculate backend" arc executing remediations 1-6 moves the grade to A−;
the remaining four move it to the publishable A the operator is asking for.

Single biggest structural recommendation: **remediation 1** — the state-machine
de-globalization. It is the root from which S5's sediment, half the order-
dependence hazards, and the reentrancy debt all grow, and it is the one change
that makes the backend architecturally indistinguishable from the house style it
was told to match.
