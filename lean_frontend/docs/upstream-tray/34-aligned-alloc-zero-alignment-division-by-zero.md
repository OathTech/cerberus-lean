# `aligned_alloc(0, n)` kills the tool with an uncaught `Division_by_zero` (Core `rem_t` by zero in the `aligned_alloc` proxy has no guard)

**Affected:** `runtime/libcore/std.core:380-393` (`aligned_alloc_proxy`;
`:385` `if size rem_t align = 0 then …` with no check on `align`);
`memory/concrete/impl_mem.ml:11-12` (`integerRem_t = (mod)` = `Z.rem`,
`integerRem_f = Big_int_Z.mod_big_int` — both raise on a zero divisor),
`:2481-2484` (`Concrete.op_ival`: `IntRem_t`/`IntRem_f` call them
unguarded, while `IntDiv` at `:2479-2480` IS guarded: `if equal n2 zero
then zero else div n1 n2`), `:1247-1265` (`allocator`: `quomod z align`
at `:1252` would also raise for `align = 0` if the `rem_t` were passed).
Checked against `master` @ `b9aeedcb4`: `std.core` byte-identical;
`impl_mem.ml` byte-identical through :2998.

## Description

The `aligned_alloc` proxy validates `size` against `align` with a Core
remainder before allocating, and never validates `align` itself. For
`align = 0` the Core `rem_t` reaches `Concrete.op_ival IntRem_t`, whose
OCaml implementation is `Z.rem`, which raises `Division_by_zero`. Nothing
catches it: the tool dies with an internal error instead of a verdict.
Two aspects:

1. **The library semantics.** C11 §7.22.3.1#2: "The value of `alignment`
   shall be a valid alignment supported by the implementation" — a
   `shall` outside a constraint, so violating it is undefined behaviour in
   C11 (§4#2). C17 (DR 460) changed the Returns clause to "If the value of
   `alignment` is not a valid alignment supported by the implementation
   the function shall fail by returning a null pointer." Zero is not a
   valid alignment under either edition, so the intended answer is a UB
   verdict (C11) or `NULL` (C17) — never a crash.
2. **The Core operator.** `rem_t`/`rem_f` by zero is undefined for the
   pure Core operator as well: `IntDiv` was given an explicit zero guard
   (`:2479-2480`), the remainders were not. Any Core program (hand-written,
   generated by another front end, or a future proxy) can therefore crash
   the interpreter; the C elaboration itself guards `%` with
   `UB045b_modulo_by_zero` before the Core operator is reached, which is
   why ordinary C never hits this.

## Observed vs expected

- Observed: uncaught `Division_by_zero`, exit 125.
- Expected: a UB verdict for an unsupported alignment (C11 reading), or
  `Specified(NULL)` (C17 reading) — and, independently, a Core `rem_t` by
  zero that yields a UB verdict (`UB045b_modulo_by_zero` or a Core-level
  code) rather than an OCaml exception.

## Impact

Low frequency in real code (`aligned_alloc(0, …)` is a caller bug), but
it is a tool crash on a program the model should judge, and the
unguarded remainder is a latent crash for every Core producer. For our
Lean port the crash has no logical meaning to mirror: its total
remainder makes `8 rem_t 0` fail the size test and report the proxy's
`DUMMY(align_alloc)` UB for `(0, 8)`, and `(0, 0)` reaches the allocator
— a divergence we are holding open until the intended meaning is fixed
here (we would rather mirror a defined answer than an exception).

## Proposed remedy

Both halves, since they are independent:

- `std.core:385`: validate the alignment first, e.g.
  `if align = 0 \/ not (is_power_of_two(align)) then pure(Specified(NULL('void')))`
  for the C17 semantics (or `pure(undef(<<…>>))` with a dedicated UB code
  if C11's UB reading is preferred; `<<DUMMY(align_alloc)>>` is the
  existing placeholder), then the existing `size rem_t align` test.
- `impl_mem.ml:2481-2484` (and the other memory models' `op_ival`):
  give `IntRem_t`/`IntRem_f` the same zero guard `IntDiv` has, or — better
  for the interpreter as a whole — make `rem_t`/`rem_f`/`/` by zero a
  Core-level UB in `core_eval`'s `PEop` evaluation so that no Core text
  can raise an OCaml exception through arithmetic.

## Classification

**TRUE BUG** (tool crash on a program the model should judge; a missing
guard, with the `IntDiv` guard three lines above showing the intended
shape). The C11-vs-C17 choice of verdict for an invalid alignment is
upstream's call; either is better than the exception.
