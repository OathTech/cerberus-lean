## 3. What the bump buys

- `lake env leanchecker <modules>` (today's named gate) keeps working unchanged:
  it replays the named modules' own constants into an environment imported
  from the `.olean`s as given; no axiom policy, no sandbox.
- `lake check` (new): builds the default targets, exports them and replays the
  **whole closure** (~58k declarations) in a fresh kernel, erroring on
  non-standard axioms, inside a `bwrap` sandbox. `--paranoid` adds five
  independent checkers (`leanchecker-paranoid`, `lean4lean`, `nanoda`,
  `con-leche`, `con-ron`); observed accepting a scratch package in 3 m 42 s
  without the sandbox. `lake comparator` checks a solution against a trusted
  statement set (not needed for the bump).
- **Box prerequisite, operator-side:** the sandbox needs unprivileged user
  namespaces; this box has `kernel.apparmor_restrict_unprivileged_userns = 1`
  and no bwrap profile, so `bwrap` fails (`setting up uid map: Permission
  denied`, inside nono; expected the same outside). Until a root-side decision
  (AppArmor profile, sysctl or setuid bwrap, all machine-global), only
  `lake check --inadvisably-no-sandbox` runs here, a speedbump by the
  container's own rule. The sandbox reads only the project directory, so run
  `lake check` from `lean_frontend/` (speclab's `path = ".."` would not resolve).
