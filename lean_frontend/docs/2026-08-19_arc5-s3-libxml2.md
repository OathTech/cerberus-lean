## Battery construction (mechanical)

Point set: for every interval boundary b in chvalid.c's tables — the six
`xmlCh{S,L}Range` tables (322 intervals: BaseChar 197, Char 2+1,
Combining 95, Digit 14, Extender 10, Ideographic 3; counts cross-checked
against the `xmlChRangeGroup` descriptors) AND the 9 maximal 1-runs of
`xmlIsPubidChar_tab[256]` — the edges b-1, b, b+1; plus fixed probes 0x0,
0x7F, 0x80, 0xFFFF, 0x10000, 0x10FFFF. Total: 331 intervals -> **1354
distinct code points**. Per point, 22 observations: the 8 exported
functions (cross-TU calls into chvalid.c), the 8 `xmlIs*Q` group macros
(expanded in the battery TU), and 6 direct `xmlCharInRange` calls against
the exported groups. Observations accumulate into an unsigned checksum
(defined wrap-around arithmetic only) printed and returned from `main` —
compared via the batch verdict line (value + stdout + stderr + blocked).

## Resource findings (drove two design decisions)

1. **Exhaustive mode is combinatorially infeasible at this scale** on
   BOTH sides: OCaml `--mode=exhaustive` yields 175 identical executions
   for a 2-call chvalid program and did not finish a 42-call program in
   5 min. Hence the single-trace seam: OCaml side runs its default
   `--mode=random` (one trace; `smt2.ml:23-31` `with_backtracking`).
   [corrected per arc-5 audits] That PRNG is TIME-SEEDED PER RUN, not
   default-seeded: `util/cerb_any.ml:1` runs `Random.self_init` at module
   load (`Cerb_any.bounded_integer` is linked into the driver via
   generated `core_run.ml:1099`), and `driver_ocaml.ml:153/190` call
   `Random.self_init` in batch_drive/drive — so the oracle's trace may
   vary across runs. Lean side gains `CerbND.runND1` + `--first` (always
   branch index 0; this equals the LAST execution of the exhaustive
   list — exhaustive mirrors OCaml's prepend order — not exhaustive's
   execution 0). Trace-selection divergence recorded in `CerbND.lean`;
   the differential is sound because this battery is PURE (verdict
   trace-independent — empirically all 175 exhaustive verdicts of the
   probe program were identical), NOT because the oracle is
   deterministic. A trace-sensitive battery would FLAKE, not
   deterministically fail, and is forbidden in this gate without a
   seed-pinning story.
2. **Exec cost is quadratic in program length** (both interpreters retain
   dead allocations): OCaml 100 pts 4 s / 200 pts 16 s / 400 pts 66 s /
   1354 pts > 300 s; Lean `--first` 100 pts 139 s. One whole-battery
   program blows the 300 s per-invocation cap on BOTH sides, so the
   battery is emitted as 28 slice programs of <= 50 points, each its own
   2-TU link; the slices partition the same point set. Measured per
   slice: OCaml ~1.2-2.7 s / ~85 MB; Lean ~22-95 s / ~107 MB peak —
   every invocation comfortably inside `ulimit -v 4000000` + 300 s.

## Stretch (probe's 4-TU uri harness) — arc-6 baseline

10-URI corpus (valid / invalid / edge) over `xmlParseURISafe`, 5 TUs
(harness + uri.c + xmlstring.c + xmlmemory.c + globals.c):

- **ORACLE_LIBC** (OCaml, WITH libc — the probe's invocation): full
  corpus executes; checksum h=546321043; 1.05 s / 201 MB. Hard ceiling
  confirmed at corpus scale.
- **OCAML_NOLIBC**: exec fails —
  `calling an unknown procedure: Symbol(118, SD_Id("memset"))`.
  uri.c's closure needs the C-libc .core surface, which `--nolibc`
  excludes; NOT a Lean-side defect.
- **LEAN** (`--batch --first`, links no C library by design): the 5-TU
  frontend + Core_linking **succeeds** (2.2 s / 240 MB for ~62 MB of
  cabs-json), and exec fails with the IDENTICAL missing procedure —
  same `Symbol(118, SD_Id("memset"))`, same symbol number. The Lean
  pipeline is at exact parity with OCaml `--nolibc` on this closure.

Arc-6 scope statement this yields: the delta between LEAN and
ORACLE_LIBC is precisely the C-libc loading story (runtime `libc.co` /
`libc.core` into the Lean pipeline); first missing symbol is `memset`.
Recorded as a fail-closed reporting baseline
(`tests/libxml2/uri_baseline.txt`, gate `scripts/test_libxml2_uri.sh`):
any drift — regression or unrecorded improvement — fails the gate until
the baseline is updated with justification.
