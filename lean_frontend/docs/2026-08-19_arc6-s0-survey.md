## (a) The libc artifact + prototype prior art

### a.1 What OCaml loads when libc is on

**Artifact.** `runtime/libc/libc.co`, built into
`_build/default/runtime/libc/libc.co` (2,944,617 bytes; siblings
`libc_inner_arg_temps.co` 2.9 MB, `libm.co` 143 KB). It is **not text**:
one version line + an **OCaml `Marshal` blob** of a `core_dump` record —
observed header `ocaml:5.4.0+cerb:git-24c3314c0+mem:concrete`.

- `core_dump` type: `backend/common/pipeline.ml:621-630` — fields
  `dump_main`, `dump_calling_convention`, `dump_tagDefs`, `dump_globs`,
  `dump_funs`, `dump_extern`, `dump_funinfo` (maps serialized as assoc
  lists; comment at :617-620 explains Marshal can't take closures).
- Writer: `write_core_object`, `pipeline.ml:674-690`.
- Reader: `read_core_object`, `pipeline.ml:648-672` — version-string
  warning on mismatch (:650-654); rebuilds Pmaps; when **not** `is_lib`
  it calls `print_core` (:668-670) — this is load-bearing below.
- Build rule: `runtime/libc/dune:132-141` — `cerberus --nolibc
  -I include -I include/posix --sequentialise --rewrite -o libc.co
  src/ctype.c src/stdio.c src/stdlib.c src/string.c src/time.c
  src/utime.c src/unistd.c src/stat.c src/uio.c src/internal.c
  src/vfscanf.c src/signal.c`. Note: the oracle's libc Core is
  **sequentialised + rewritten** (matters for path (iii) below).

**Load/link path** (`backend/driver/main.ml`):

- `create_cpp_cmd` :38-52 — without `--nolibc`, cpp gains the libc
  include dirs and `-DCERB_WITH_LIB`; `builtins.h` is `-include`d
  regardless.
- `core_libraries` :54-77 — prepends the runtime `libc` dir to the
  search path and resolves lib `"c"` → `libc.co`
  (`c_inner_arg_temps` under that switch, CHERI variant otherwise).
- `main` :150-156 — folds `frontend ~is_lib` over
  `core_libraries (not nolibc && not core_obj) … @ files`: **libc is
  loaded first, as a library**, before the user TUs.
- `frontend` :23-37 — extension dispatch: `.co`/`.o` →
  `read_core_object ~is_lib`; `.c` → C frontend + `core_passes`;
  `.core` → core frontend.
- Link+exec branch :271-299 — `Core_linking.link (f::fs)` (the same
  lem-generated linker we run: `frontend/model/core_linking.lem`), then
  exec, or `-o out(.co)` → `write_core_object` **post-link** (:293-298).

**What `--pp core` emits WITH libc.** `print_core` is invoked per-TU
inside `core_passes` (`pipeline.ml:554-580`), i.e. **before linking**,
and the library-load path (`is_lib=true`) never prints
(`pipeline.ml:668-671`). There is **no post-link pretty-print** in the
stock flow (after `Core_linking.link` only exec / `write_core_object`).
So `cerberus --pp core file.c` (libc on) prints only the user TU.

**But an unlinked-libc text dump IS obtainable from stock cerberus**
(the charter's key question — verified empirically, see a.4): passing
`libc.co` as an *input file* makes `frontend` route it through
`read_core_object` with `is_lib=false`, which pretty-prints it:

```
cerberus --nolibc --pp=core --pp_core_out=libc_unlinked.core \
    _build/default/runtime/libc/libc.co        # rc 0
# → 4,186,639 bytes / 89,582 lines: 12 globs, 191 proc/fun
#   (188 unique names), tagDefs ("-- Aggregates")
```

A **post-link** text dump is also stock-obtainable in two steps
(`cerberus <TUs> -o linked.co` then pp the `.co` as above; verified on
the 5-TU uri closure: 11,218,477 bytes).

**Critical limitation of the text form.** `Pp_core.pp_file`
(`ocaml_frontend/pprinters/pp_core.ml:843-884`) prints only tagDefs,
globs, and the fun map. It **never prints the `extern` map**
(`pp_extern_symmap` :811-815 is CLI-dead), never prints `main`, and
prints `funinfo` only under `show_include` (module `All` :928-936 —
unreachable from the CLI: `print_core` `pipeline.ml:536-549` selects
Basic/WithStd/WithLocations/WithLocationsAndStd, all
`show_include=false`). Both maps are load-bearing for exec:

- `extern`: linking keys on it (`core_linking.lem:10-47 link_extern`);
  the driver's decl→def substitution map is built from it
  (`driver.lem:63 core_extern`).
- `funinfo`: `Eccall` argument conversion looks up the callee
  (`core_run.lem:952-967`, hard `error "Eccall : function … not
  found"`), return conversion (`core_reduction.lem:1114-1129`), also
  `core_eval.lem:906`.

So ANY text/`.core` ingestion path must reconstruct `extern` +
(at least partial) `funinfo` on the Lean side — see a.4.

### a.2 Prototype prior art (mandated study) [USER mandate; findings factual]

**How it ingested libc: it didn't ingest libc as such — it let a
*patched* OCaml cerberus link everything (libc included) and dumped the
post-link, typechecked Core as JSON.**

- The prototype's cerberus submodule carries a bespoke backend:
  `cerberus/ocaml_frontend/pprinters/json_core.ml` (1,270 lines; recent
  submodule commits "Add missing fields to JSON Core export", "Add type
  annotations…", "Add annots field…") plus a driver flag
  `--json_core_out` (`cerberus/backend/driver/main.ml:456-458`).
- Dump site `main.ml:269-283`: **after** `Core_linking.link`, with
  comment "*done after linking so libc is included*", after
  `Core_typing.typecheck_program` (for type annotations).
- `json_file` (`json_core.ml:1236-1258`) emits main, tagDefs,
  **stdlib**, impl, globs, funs, **extern** (`json_extern` :1200-1207),
  **funinfo** (`json_funinfo` :1150-1167) — i.e. the prototype had to
  patch in exactly the sections the stock pretty-printer lacks.
- Harness `scripts/test_interp.sh`: per test file it runs OCaml
  `--exec --batch` (10 s timeout, :215), then re-runs cerberus with
  `--json_core_out` (:318-321), then `cerblean_interp --batch <json>`
  (:327-329). `--nolibc` is an opt-out flag (":83 --nolibc  Skip libc
  linking (2MB vs 200MB JSON, faster)"); prototype `CLAUDE.md:203`
  records the same 2 MB vs 200 MB claim and "full suite is expensive
  (1-2 hours)". **No stripping, no laziness, no subsetting anywhere in
  the interp path** — the interpreter eats the whole post-link JSON
  every time.
- `scripts/strip_core_json.py`: reachable-from-`main` closure by
  **symbol NAME** (`find_calls` :15-33 — any `{tag:"Sym"}`/`name` hit),
  keeps only reachable stdlib+funs; `--strip-locs` (Region→null),
  `--strip-funinfo`, `--strip-extern` (:74-129). Wired **only** into
  `test_genproof.sh:172-173` (proof generation), never into the
  interpreter harness.

**Empirical reproduction** (one small file,
`tests/minimal/001-return-literal.c`, caps as above):

| probe | result |
|---|---|
| `--nolibc --json_core_out` | 3,691,405 B; interp OK in 0.11 s |
| WITH libc `--json_core_out` | **365,440,360 B**, 8.6 s wall to dump (the "2 MB vs 200 MB" claim reproduced, now 99×; the submodule's later type/annot additions grew it) |
| prototype interp on the 365 MB JSON | **`INTERNAL PANIC: out of memory` at ~0.95 s under the 4 GB cap** (its own harness ran uncapped) |
| `strip_core_json.py` default / `--aggressive` | → 17,350,226 B (4.7%) / 10,866,555 B (3.0%), 1.9 s |
| prototype interp on EITHER stripped form | **fails**: `pure function call (some all_values_representable_in): not found in stdlib or funs` — the name-based reachability drops an impl-referenced stdlib dependency on even the smallest test |

**What transfers to our situation** (text CoreParser + arc-5
Core_linking): (1) hard evidence that `extern` + `funinfo` are required
for post-link exec — the prototype patched OCaml precisely to get them;
(2) the scale law: post-link whole-program dumps are per-test and
enormous (the unlinked libc artifact, by contrast, is 4.2 MB **once**);
(3) a negative result on subsetting: name-based reachability is
demonstrably unsound — any subset strategy must operate on real symbol
references or not at all; (4) its varargs design (§c) is faithful and
transfers to S2.

### a.3 The uri closure's undefined symbols (empirical) and coverage's libc wants

Method: link the 5-TU closure (`uri_harness.c`, `uri.c`, `xmlstring.c`,
`xmlmemory.c`, `globals.c`) with `--nolibc` into a `.co`, stock-pp it to
text, then diff the function names referenced as `Cfunction(N)` against
`^proc/^fun` definitions. 86 referenced function names, 142 defined,
**25 unresolved**, in three classes:

- **libc wants (5)** — all present in the libc dump (verified):
  `memset` (the known first blocker; identical
  `Symbol(118, SD_Id("memset"))` failure both sides, uri baseline),
  `strlen`, `snprintf`, `vsnprintf`, `fprintf`.
- **already-working proxy surface (5)**: `malloc_proxy`, `free_proxy`,
  `realloc_proxy`, `memcpy_proxy`, `printf_proxy` (arc-5 std.core
  ailname linking; not in and not needed from libc).
- **out-of-closure libxml2 (15)** — statically referenced, dynamically
  unreached; libc does not and need not provide them:
  `xmlCleanupMutex`, `xmlGenericErrorDefaultFunc`, `xmlGlobalRandom`,
  `xmlGrowCapacity`, `xmlInitMutex`, `xmlInitParser`, `xmlMutexLock`,
  `xmlMutexUnlock`, `__xmlParserInputBufferCreateFilename`,
  `xmlPrintErrorMessage`, `xmlResetError`, `xmlSAX2GetColumnNumber`,
  `xmlSAX2GetLineNumber`, `xmlSAX2GetPublicId`, `xmlSAX2GetSystemId`.

Load-bearing observation: **ORACLE_LIBC runs the full 10-URI corpus
(exit 0, h=546321043, committed baseline) with those 15 symbols still
undefined** — unknown procedures only fail at call time, on both sides.
The libc artifact therefore does NOT need to close the static closure;
"loading libc" (the same subset the oracle loads) is exactly sufficient.

**Coverage corpus libc wants beyond the proxies** (today CERB_SKIP —
OCaml `--nolibc` fails them too, so they're outside the comparable set):
`exit` (builtin-006-exit.libc.c), `puts` (io-004-puts.libc.unsupported.c),
`calloc` (libc-002), `memset` (libc-011), `strlen` (libc-012). All five
are defined in the libc dump (verified: `proc exit/puts/calloc/memset` +
`fun`/`proc strlen`). A libc-enabled coverage mode would move these from
CERB_SKIP into the differential (§b).

### a.4 Pricing the three ingestion paths + recommendation

**The charter's key technical question, answered definitively: YES —
stock cerberus emits UNLINKED libc Core as text with no OCaml patching**
(`cerberus --nolibc --pp=core --pp_core_out=… libc.co`, verified rc 0,
§a.1). Caveat, equally definitive: the stock text form carries **no
extern map, no funinfo, no main** — those exist only inside the
marshalled `.co` (or the prototype's patched JSON).

Operator principle for this decision `[USER]`: *choose the path that
minimizes the TCB* — new code we write grows the trust surface by what
we write; leaning on Cerberus grows the surface that cannot be reasoned
about; the balance turns on what stock cerberus already offers.
Analytical frame applied below `[AGENT]`: (1) Lean-side linking via the
**generated** `Core_linking` is lem-derived — inside the reasoned-about
surface — so path (i)'s marginal new code is only artifact ingestion,
and CoreParser is already a trust surface for `std.core` (usage grows,
mechanism doesn't); (2) a post-link dump is not a thin syntax boundary
like cabs-json — linking is a *semantic* transformation, so
oracle-trusting it enlarges the unreasoned surface qualitatively;
(3) since stock cerberus CAN emit the unlinked artifact, (i) needs no
upstream work at all.

**Path (i) — unlinked libc text dump, linked by our arc-5 Core_linking.**

*Work priced (measured):* our CoreParser currently fails on 68 of the
191 libc decls + all 12 globs. Isolated gap classes (mini-reproducers,
each verified independently):
1. no `glob` top-level production (globals with `[ail_ctype = '…']`
   attribute + initializer expression — 12 in libc);
2. ctype grammar: `restrict` qualifier (`'char*restrict '`) — FAIL;
3. ctype grammar: variadic marker (`'signed int (*) (const char*, ...)'`)
   — FAIL (plain function-pointer ctypes parse OK).
Zero-arg procs, `NULL(struct T*)`, `_Atomic(...)` all parse OK today.
More classes may surface behind these (68 failures collapse onto the
probes above but were not exhaustively re-parsed); the shape is
bounded: CoreParser's ctype-literal grammar + one new production.
Parse scale: `std.core` (36 KB) parses inside a 0.024 s total run; the
libc dump is 115× that → ~1-3 s per libc-enabled invocation
(extrapolated; measured post-S1), confined to libc-enabled modes.

*Metadata reconstruction (the real new code):*
- `extern` synthesis for a **library** TU is principled and small:
  every top-level `proc`/`fun`/`glob` with an `SD_Id` name exports
  `ident → ([sym], LK_normal sym)`; the generated `link_extern` does
  the rest. Must be drift-checked against oracle behavior
  differentially (the uri gate itself is that check).
- `funinfo` is needed only for symbols that are **`Eccall`ed with a
  libc-side callee sym** — user-TU funinfo already covers user-side
  call sites (per-TU funinfo includes declared-only functions; lookup
  at `core_run.lem:954` uses the caller-side sym). Options for the
  libc-internal residue, S1's choice: name-join against a Lean-desugared
  declarations-only TU (all-Lean), or a small synthesized table for the
  needed subset. This is the least-clean part of path (i); it is
  bounded and Lean-side.

*TCB accounting (i):* new code = CoreParser grammar growth (existing
trusted mechanism), extern/funinfo synthesis (small, new, inside the
reasoned Lean surface, differentially checked). Oracle-trusted = the
dump artifact itself: elaboration+sequentialise+rewrite of libc's C
sources — the **same trust class as cabs-json and std.core** (both
already oracle-produced pinned inputs), pinned + drift-checked
(regeneration is one stock command; pin the md5 of `libc.co`, the md5
of the dump, and the version header line). Linking is exercised in the
lem-generated, reasoned surface. **No upstream/OCaml work — the
charter's tripwire is not approached.**

**Path (ii) — post-link whole-program dump (prototype-style).**
Stock-obtainable as text in two steps (better than the prototype's
1,270-line JSON patch — a genuine finding), but: it has the **same**
parser gaps and the **same** missing extern/funinfo problem, except the
post-link extern map spans all TUs and its content encodes
tentative-definition resolution — synthesizing it by name amounts to
re-implementing linking informally; per-program artifacts are ~11-15 MB
each and every one is oracle-produced input; and it bypasses not just
our linker but the entire Lean frontend (cabs-json → desugar →
typecheck → translate) for every libc-enabled test — the differential
stops testing what we ship. *TCB accounting (ii):* less new code only
superficially; the **link step itself becomes oracle-trusted** — a
qualitative enlargement of the unreasoned surface (frame item 2) — and
what it would un-exercise is precisely arc-5's Core_linking +
multi-TU digest machinery plus the whole frontend on libc-enabled runs.
Prototype evidence: this shape needed an OCaml patch for metadata and
hit the scale cliff (365 MB / OOM).

**Path (iii) — parse libc's C sources through our own pipeline.**
Cleanest metadata story (elaboration produces extern+funinfo natively;
no new parser code; smallest oracle surface — just cabs-json per libc
TU, the existing boundary). Disqualifying asymmetry: the oracle's libc
is **sequentialised + rewritten** (`runtime/libc/dune:138`), and our
pipeline implements neither pass — the two sides would execute
*different* libc Core (unseq elimination changes ND/trace structure),
breaking the identical-input premise of the differential at its heart;
fixing that means porting `Core_sequentialise`/rewrite (a real new
semantic surface, weeks) or documenting divergence inside the gate.
Plus an untested desugar frontier over musl-derived C (`vfscanf.c`,
`stdio.c`…) in the middle of an arc with a hard bar. *TCB accounting
(iii):* smallest oracle-trusted surface, largest new-code surface, and
a semantic-equivalence gap (sequentialise) that neither surface covers.

**Recommendation `[AGENT:S0]`: path (i).** Under the operator's
TCB principle it dominates: its marginal additions land in existing
trusted mechanisms (CoreParser) or the reasoned lem-generated surface
(Core_linking), and its only oracle-trusted input joins an
already-established artifact class (pinned, regenerable by one stock
command, drift-checked). Subset strategy: **ship the full 191-decl dump
first** — 4.2 MB parses in seconds and 191 decls is not 365 MB; add
pin-time subsetting only if S1 measurement bites, and if so compute the
subset from real linked-symbol references, never by name scan (the
prototype's negative result). Explicitly NOT recommended: any OCaml-side
dump-mode patch — stock output + Lean-side synthesis stays inside the
tripwire.

| 50 | 54.30 s | 2.23 s |
| 100 | 288.8 s (**over the 300 s cap already at ~100 points**) | (arc-5: ~400 pts 66 s) |

Lean/OCaml ratio grows 15× → 24× → ~29× (N=25/50/100); N=50→100 is
2× points → 5.3× time. maxRSS flat ~100 MB (not memory-bound).

**Discriminating probe — the charter's likely-shape is incomplete.**
A constant-memory-state control (loop rewriting ONE byte; bytemap size
fixed at ~a dozen entries; no allocation churn):
512 iterations 0.30 s → 4096 iterations **>300 s timeout** (Lean),
vs OCaml 0.09 s → 0.41 s (linear). So the dominant Lean-side defect
degrades **per executed step at constant memory state** — it is NOT in
CerbMem's assoc lists at all. Two structures explain everything:

1. **LemLib `Fmap` — every generated lem `map` is an assoc list with
   O(n) insert and O(n) lookup.**
   `lem-lean/lean-lib/LemLib.lean:339-351`: `Fmap α β := List (α × β)`;
   `fmapAdd` = cons + **full filter of the map on every insert**;
   `fmapLookupBy` = linear scan. The OCaml backend maps the same lem
   `map` to **Pmap (balanced tree)** — e.g. the per-thread Core
   environment: `env: list (map sym value)`
   (`core_run_aux.lem:212`) is `(sym, value) Pmap.map list` in generated
   OCaml (`ocaml_frontend/generated/core_run_aux.ml:217`) but
   `List (Fmap sym value)` in generated Lean. Every Core-level binding
   pays O(|scope|) twice (filter + later lookups), and scopes grow with
   executed steps → superlinear at constant memory, exactly as measured.
   This is a **documented Lean/OCaml representation divergence in the
   runtime library**, not in the mirrored semantics.
2. **CerbMem byte/allocation assoc lists** (the arc-5 D5 register item,
   real but secondary): `writeBytesTo` filters the ENTIRE bytemap per
   store, `readBytesFrom` does `find?` per byte
   (`CerbMem.lean:1095-1104`); bytemap only grows (kill never prunes
   bytes — faithfully mirroring OCaml, whose own quadratic seam is the
   `dead_allocations` `List.mem` inside `find_overlaping`,
   `impl_mem.ml:667,761-800`). OCaml at the same seam:
   `module IntMap = Map.Make(Z)` (`impl_mem.ml:93`), state fields
   :482-501 — O(log n) per byte vs our O(n).

**A third, hard-edged finding: a stack ceiling.** Micro loops of
~2k-8k iterations intermittently die with SIGABRT (stack overflow in
the step/ND recursion) rather than run slow — reproduced at 2048/8192
iterations while 4096 sometimes runs to timeout instead. The 50-point
battery slices are safely below it; a 339-point slice (the ≤4-slice
bar) with ~22 calls per point may not be. This is a separate defect
(recursion depth in the runner), newly observed, register-worthy.

**Candidate replacement + iteration-order argument.** Replace the map
REPRESENTATIONS, not the semantics: (1) LemLib `Fmap` → an ordered tree
keyed by the existing `MapKeyType.mapKeyCompare` (one definition site in
`lean-lib`); (2) CerbMem `bytemap`/`allocations` (and siblings) →
`Std.TreeMap Int` keyed like `Map.Make(Z)`; keep `deadAllocations` a
List (mirrors OCaml exactly, preserving the oracle's own asymptotics).
Iteration-order preservation: OCaml folds Pmap/IntMap in **ascending
key order**; compare-keyed trees fold in ascending key order with the
same total order — every observable fold (e.g. `link_extern`'s
`Map_extra.fold`, `find_overlaping`'s double-alloc detection order)
would match the ORACLE's order, which today's insertion-ordered lists do
NOT guarantee. The change is a parity improvement, not a divergence;
keyed lookups are order-free. Estimated effect: per-step map costs drop
O(n)→O(log n) at both seams; expect Lean back inside a single-digit
multiple of OCaml on the battery (OCaml-extrapolated ~47 s per
339-point slice; Lean at 5-10× → 240-470 s — the ≤4-slice bar is
plausible, not assured, and additionally gated on the stack ceiling).

**Do-or-park `[AGENT:S0]`: DO, reshaped.** The charter's S3 likely-shape
(CerbMem lists alone) would NOT meet the bar — the measured dominant
term is LemLib's Fmap, i.e. **the fix crosses into lem-lean's lean-lib
and triggers the full two-repo pin dance** (charter expected zero lem
changes; this is exactly the class of finding S0 exists to surface).
Recommended S3 sequence: (1) one instrumented build to split
env-map vs bytemap cost on a real slice (bounded, half-day); (2) the
LemLib Fmap representation change behind the existing `MapKeyType`
interface + pin dance; (3) CerbMem TreeMap swap; (4) re-measure against
the ≤4-slice bar with ZERO differential movement, park per the
charter's clause if the constant or the stack ceiling still binds —
the stack defect is priced as its own register item, not silently
absorbed into S3.
