## CoreParser extensions (task 2) — mechanism trusted, usage grows

Bar met: **all 260 top-level declarations of the pinned dump parse —
191 procs + 68 globs + 1 tagDef, full file in 0.37 s** (unit-tested
counts in `test/Unit/CoreParserTest.lean`, plus a reproducer test per
production). New productions, each cited at its implementation site:

1. **Bodyless ProcDecl** `proc f (bTy, …)` — pp_core.ml:783-785. A
   PP-ONLY form: core_parser.mly has no production for it
   (proc_declaration mly:1803-1809 requires named params + body). The
   unprintable return base type is recorded as BTy_unit (unread:
   call_proc rejects non-Proc entries, core_run.lem:46-51).
2. **Two ctype printer dialects.** Embedded-AST ctypes print via
   Pp_core_ctype (pp_core.ml:227-228: `long_long`, `ichar`, postfix
   function types, qualifiers never printed); ctype VALUES print via
   Pp_ail.pp_ctype (pp_core.ml:332: `long long`/`long double` spaces,
   `(*)`/`(*[N])` fn-ptr declarators, `(void)` empty prototypes,
   post-star qualifiers `char*restrict`, variadic `, ...`). The parser
   accepts the union, forking only the genuinely ambiguous empty-parens
   case (AIL `()` = FunctionNoParams, pp_ail.ml FunctionNoParams case;
   CORE `()` = Function [] false — the pp_core_ctype print of both is
   identical, documented choice). Post-star qualifiers land in
   Pointer's pointee-qualifier slot or the parameter triple, exactly
   inverting pp_ail.ml:238-317's `aux`.
3. **Tag symbol identity.** Struct/union tags now intern by name-hash
   everywhere (previously ctype-position tags were `Symbol "" 0` —
   never exercised by exec, since std.core has no tags).
   OTy_struct/union positions print via Pp_symbol.to_string
   (`name_num`, pp_symbol.ml:5-10 via pp_core.ml:186-189) — a trailing
   `_<num>` strip recovers the name (`struct _IO_FILE_331` ≡
   `'struct _IO_FILE'`); a unit test asserts no top-level name aliases
   under the strip.
4. **`error("…", pe)`** — dquoted string form (pp_core.ml:444-445,
   grammar STRING mly:1572); the `<<<…>>>` spelling remains for
   hand-written std.core.
5. **Unannotated list literals** `[(…), …]` — pp_value's Vlist prints
   bare brackets (pp_core.ml:327-329), unlike the grammar's annotated
   form; element type recorded as BTy_unit (Cnil/Vlist types unread in
   matching, core_aux.lem:2028-2035, 2426-2429).
6. **`Cfunction(sym)` → real `PVfunction`** (impl_mem.ml:567-568).
   Previously parsed to a null pointer (matching the mly's own TODO
   punt at :1540-1541) — now load-bearing: every libc-internal call
   goes through `Specified(Cfunction(f))` + `cfunction(…)` guards.

### Two reparse-ambiguity classes fixed [AGENT:S1 — resolution rules]

The pp NEVER parenthesizes PEif (precedence_pexpr `None`,
pp_core.ml:69-98 + compare_precedence :161-164) and never parenthesizes
expression sequences (Esseq unit-pattern prints `e1 ; hardline e2`,
pp_core.ml:648-649). Both make the token stream ambiguous; both were
previously mis-parsed SILENTLY (test_core.sh only checks parse
success — this became observable the moment parsed Core EXECUTED):

* **PEif as binop operand** (the elaborator's integer-promotion wrapper
  `if all_values_representable_in(…) then conv_int(…) else conv_int(…)`,
  the only generator of the shape; 39 `if if` sites in the dump). Rule:
  an `if` parsed as a binop RHS (minPrec > 0) or as the leading atom of
  an if-condition gets atom-bounded branches; all other ifs stay greedy
  (std.core NEEDS greedy branches: `else 2^width + n`, std.core:143;
  verified std.core contains no binop-then-`if` and no `if if`).
* **Layout-sensitive `;`.** `if c then … else pure(Unit) ; rest` —
  where `rest` is the rest of the procedure — re-associated `rest` into
  the else branch under greedy parsing (found via the libc fwrite path:
  a C `if` without else compiles to exactly this shape, and the panic
  `PEcase, mismatched ==> Unit` was the mis-nested value escaping).
  Disambiguator: layout, mirroring the pp — Esseq sequels sit at the
  SEQUENCE's own indentation (hardline, never flattened), branch bodies
  strictly deeper (P.nest 2). Rule: a `;`-sequel is consumed only if
  its first token's column ≥ the column of the current sequence's first
  expression. Both directions unit-tested (outdented sequel attaches to
  the sequence; indented sequel stays in the branch).

## Extern/funinfo/tagDefs synthesis (task 3)

What OCaml's loader has: `read_core_object` (pipeline.ml:648-672)
deserializes the marshalled `core_dump` — main, calling_convention,
tagDefs, globs, funs, extern, funinfo (record: pipeline.ml:621-630) —
reconstructing NOTHING; stdlib/impl come from the load context
(:657-660), loop_attributes/visible_objects_env are set EMPTY
(:661-663). The text dump lacks extern, funinfo, main, and the header
tagDefs entirely.

**Design [AGENT:S1] — metadata from our own elaboration of the same 12
sources.** `Main.loadLibc` splits the library file:

* **Bodies** (funs + globs, file order) from the pinned dump via
  CoreParser.
* **Metadata** (extern, funinfo, tagDefs, calling convention) by
  frontending the SAME 12 libc TUs (dune order) through our own
  desugar/typecheck/translate and linking them with the generated
  Core_linking — the identical pipeline that produced libc.co's
  metadata oracle-side (extern: translate_extern_map,
  translation.lem:4505-4511; funinfo/tagDefs: translation.lem:4521-4540;
  merge: link_aux/link_extern, core_linking.lem:10-46, 286-316). The
  oracle's extra `--sequentialise --rewrite` are Core-to-Core BODY
  passes and do not touch this metadata. This keeps linking AND
  metadata inside the reasoned surface; the only oracle-trusted input
  remains the pinned dump. (Measured: the 12-TU metadata frontend+link
  costs < 1 s.)
* **The stitch**: metadata symbols are rekeyed BY NAME onto
  CoreParser's interned symbols — accepting exactly the descriptions
  the pp prints as plain names (SD_Id/SD_ObjectAddress/SD_FunArgValue,
  pp_symbol.ml:20-24). std.core proxy symbols in funinfo (exit_proxy
  etc., created by ailname substitution at elaboration,
  translation.lem:244-251) are already interned — rekeying is the
  identity on them. Name-join collisions fail closed after structural
  checks:
  - tagDefs: same-name tags from multiple TUs must agree memberwise
    (same headers ⇒ they do);
  - funinfo: must agree on return/param ctypes and variadic;
    **has_proto is excluded** — declaration-TU vs definition-TU entries
    disagree on it (__strtox/__strtoxd), the oracle keeps both under
    distinct syms, and has_proto is verified UNREAD by the pinned
    bodies (all 339 cfunction 4-tuple binders bind it to a dead
    variable — checked mechanically);
    **CORRECTION (2026-08-19, arc-6 S5f, per audit-2):** the binder
    count above originally read 221 (a whitespace-brittle grep);
    audit-2's whitespace-tolerant recount over tests/libc/libc.core
    gives 339 binders, all 339 binding has_proto to a dead variable —
    the UNREAD conclusion is unchanged. Same correction applied to
    Main.lean's module note.
  - fun map: Proc definitions win over ProcDecl entries per symbol;
    duplicate Proc definitions (static __procfdname in two TUs,
    alpha-equivalent bodies, conflated by name interning) keep the
    first.
* Assembly mirrors read_core_object: main = none (library; link_main
  tolerates it, core_linking.lem:50-57), stdlib/impl from context,
  loop_attributes/visible_objects_env empty (also preserves
  safe_map_union disjointness at link).

Documented divergences from the oracle's in-memory libc file (all in
Main.lean's module note): funinfo param-name syms dropped (`none`;
runtime reads only ctypes — core_run.lem:952-967 `List.map snd`,
core_eval PEcfunction `snd`), ProcDecl return bTy = BTy_unit, static
name conflation (structurally checked).

## Link + execute (task 4)

`--libc <pinned.core> --libc-tu <json> ×12` — explicit flags, not an
auto-load convention [AGENT:S1]: libc-enabled runs are NEW modes per
the charter; an auto-load could silently move standing corpora. The
libc file is processed FIRST, before user TUs — it lands LAST in the
reverse-consed list handed to Core_linking.link, mirroring the OCaml
driver's `core_libraries … @ files` fold (main.ml:150-156). Digests:
the pinned dump's real MD5 is set as the TU digest before parsing
(arc-5 machinery; CoreParser interning is digest-independent —
provenance-recording), and each metadata TU gets its json-content MD5
exactly like user TUs.

Symbol-invariant note re-verified (charter risk item): unit-tested —
all libc∪std top-level interned symbol ids ≥ 2^20 (above the
desugar-threaded band) and the name-hash interning is collision-free
across the 188+68 libc names ∪ std.core names. The 15 out-of-closure
xml* undefined symbols remain undefined and are tolerated exactly as
the oracle tolerates them (unknown procedures fail only at call time,
call_proc core_run.lem:68-70; the 10/10 uri run is the demonstration).

## ADDENDUM (arc-12 D2 honesty note, 2026-08-21) — libc.co is collision-exposed

Arc-12 measured the fork's own libc sources against the F-D symbol-id
margin (483): 4 of the 12 TUs are beyond it — stdio (desugar hwm
**856**), stdlib (**673**), internal (**682**), vfscanf (**521**) —
and the un-floored elaborations of three carry LIVE duplicate

(e.g. `__uflow` = `ret_526` as map keys); vfscanf's overflow is
supply-only. The pinned `libc.co` / `tests/libc/libc.core` were BUILT
from these elaborations, so every libc-mode oracle verdict rides on
collision-exposed Core objects; their correctness evidence is the
differential agreement with the protected Lean side (7/7 libc_exec,
16/16 uri). Under the D2 ruling: the pinned artifacts are
GRANDFATHERED (register entries, arc-12 S2 record); libc.co REBUILDS
are blocked by the floor until the renumbering-era re-derivation (the
mover); the 12 metadata cabs-jsons are regenerated via the
verified-sound export exemption (Cabs bytes are pre-desugar — arc-12
batch-4 evidence: beyond-margin exports byte-identical across
collision-possible and collision-impossible counter bases). No arc-6
result is changed; the trust base is now stated precisely.

## ADDENDUM (arc-13 S3 audit fix, 2026-08-22, B-F5) — pin identity is now a content hash

The version-provenance record this document introduced
(`tests/libc/libc.co.version`, the libc.co header line) proved
operationally broken as a PIN: the header embeds a git-describe
string that goes '-dirty'/stale on every rebuild, forcing spurious
re-pins after byte-identical re-derivations. It is DELETED and
replaced by `tests/libc/libc.core.sha256` — the sha256 of the dump
text, verified by `libc_prep.sh` against both the committed pin and
the freshly regenerated dump (fail-closed both directions,
plant-tested). The version header line is still printed by
`libc_prep.sh`, informationally only. The trust story above is
otherwise unchanged.
