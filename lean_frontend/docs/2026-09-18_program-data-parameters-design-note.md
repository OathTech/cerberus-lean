## 0. The question in one paragraph

Two hand-written seams still give a PURE Lean signature to a read of mutable process state: `CerberusImpl.typeof_enum` (an `IO.Ref` registry written by `register_enum` during desugaring and read by every layout function at an `enum` type) and `CerberusFresh.digest` (an `@[extern]` read of the C global holding the current translation unit's MD5, minted into every fresh symbol). Both are machine-pinned in `scripts/unsafebaseio_allowlist.txt` under the effect-erasure invariant (`docs/2026-08-22_arc14-effect-erasure-invariant.md`: "no proof may relate two such applications across a state-mutating boundary, and no theorem STATEMENT may mention such an application") with the mover "the reader/supply machinery follow-up slice". They are the LAST two: the config/switch refs left the allowlist on 2026-09-05 (plain `def`s), and every other former global is a threaded supply or a reader. Retiring them makes every layout fact at enum types and every symbol's identity a function of PROGRAM DATA the kernel can see — the property cerberus-sl states as "soundness rests on INTENDED properties of the semantics, never on accidental facts of the implementation" (their DECISIONS C3.10) — and closes the invariant page as history.

## 3. Routes

### 3.1 The enum's compatible type as program data (the uncontested item)

**Route E-A (recommended): a sibling map beside the tag definitions + a reader on Lean; the GCC rule moves into lem.**
1. `implementation.lem`: `val enum_compatible_type: list integer -> Ctype.integerType` with a SHARED body (GCC's rule, mirrored from `ocaml_implementation.ml:130-135`, cited); `val enum_definitions: unit -> map Symbol.sym Ctype.integerType` — `declare {lean} reader val enum_definitions`; OCaml target_rep = a two-line `Ocaml_implementation` function turning `!registered_enums` into the map; `typeof_enum`'s body becomes SHARED: `match Map.lookup s (enum_definitions ()) with Just ity -> ity | Nothing -> failwith "… was not registered"` (the OCaml keeps the same failure text). `register_enum` stays as the OCaml registry write (the oracle mirrors upstream); on Lean it becomes a pure `true` (the redefinition case is already caught by the `tag_definitions` check just before, `cabs_to_ail_effect.lem:1766-1770`) and the `IO.Ref`, `implemented_by`s and `initialize` are DELETED — two allowlist rows retire.
2. The desugarer records the decided type in program data: `A.sigma` gains `enum_definitions : list (Symbol.sym * Ctype.integerType)` (or the Core `file` gains `enumDefs` beside `tagDefs`; the pipeline carries it as it carries `tagDefs` — `translation.lem:4505-4511`'s assembly); at `cabs_to_ail_effect.lem:2518-2528` the `Enum_definition ns -> acc` arm becomes the map entry `(ident, enum_compatible_type ns)`.
3. The Lean entry seeds the reader from the program (where `runFile.tagDefs` is passed today: `Main.lean`, `CerbCall.lean`); `reader_consumer` seams gain a second leading argument (mechanical; `mem.lem:89-91,156,169` plus any added since — the worker enumerates); the layout functions in `CerberusImpl.lean` become functions of the map (16 sites) and `CerbMem`'s two range functions (6 sites) take it through the consumer binder; `Implementation.typeof_enum`'s `assert false`-shaped arms after normalisation become provably unreachable for registered tags. Multi-TU linking merges the maps as it merges `tagDefs`.
Ripple: lem — `implementation.lem` (2 vals + a body), `cabs_to_ail_effect.lem:2525` (one arm), `ailSyntax`/`core.lem` (one field), `translation.lem` (the assembly), `core_linking.lem` (the merge); OCaml — one tiny target_rep, NOTHING else (the ~101 layout call sites untouched); Lean — `CerberusImpl.lean` 16 sites, `CerbMem.lean` 6, `Main.lean`/`CerbCall.lean` seeding, the reader_consumer seams' signatures, `handwritten_copy.manifest` untouched; gates — the opaque census (`check_theorem_axioms.sh`) and the allowlist shrink by exactly two rows; the effect-erasure invariant page's enum paragraph becomes history; zero movement on every lane (the values are identical by construction; the OCaml is unchanged). Consumer payoff: `sizeofCtype tds (enum s)` IS a function of program data; `alignofCtype … > 0` at a registered enum is a theorem; their S3-A1 exclusion lifts.

**Route E-B (rejected):** `EnumDef of integerType` as a third arm of `Ctype.tag_definition` — forces an arm into every OCaml `match` on `StructDef/UnionDef` (impl_mem ×4 models, smt, bmc; compiler-forced) and every Lean one — a wide ripple for no gain over E-A.
**Route E-C (rejected, the consumer's (B)):** an explicit compatible-type argument on the layout functions instantiated from the registry at the exec entry — still a hidden read at the entry; the parameter is honest but the source is not program data.

### 3.2 The digest as data (the contested item)

**Route D-A (recommended IF taken): `declare {lean} reader val digest`.** `symbol.lem:44` `val digest: unit -> digest` is already the reader shape; ONE declare lifts every transitive user — the desugarer's and elaborator's `fresh_*` mints, `fresh_given_int`, `core_run`'s `fresh_symbol'`, `step_ctx`, the driver — so every minted symbol's digest is the reader VALUE the entry passed (a kernel-visible String), and the OCaml is UNCHANGED (its target_rep stays the global read; the differential stays byte-identical). The Lean entry passes each TU's digest to that TU's frontend calls (`Main.lean:637/961` already have it in hand) and the run's digest to `drive`/`initial_driver_state` (matching today's global: the value set last before the run — the worker pins WHICH TU that is from the OCaml's `set_digest` sequence and mirrors it). Consumers state `fresh_given_int P.digest m` with `P.digest` the reader argument of `drive` (visible, quantifiable), and "library `""` ≠ program `d`" becomes a theorem for any `d ≠ ""` — the entry passes a 32-hex-digit MD5, never `""` (pin it: a hermetic test that the frontend refuses an empty digest, or the entry constructs it from the file content as today). Ripple: lem — one declare; OCaml — none; Lean — the entry seeding, the reader_consumer seams' signatures (now THREE leading arguments: `tagDefs`, `enum_definitions`, `digest` in the global sorted order — mechanical), the deletion of `digestPure`/`digest_impl`/`setDigestIO` and their allowlist rows (the C global `cerb_digest_get` in `native/` retires with them; `native/md5.c` stays for the hashing). Multi-TU is the design point: with the reader each TU's symbols carry THAT TU's digest as data (today: the global at the time — the same values). `CoreParser.mkSym`'s `String.hash` numbering (item 6) is untouched; distinctness from program symbols then rests on `"" ≠ d`, a theorem.
**Route D-B (the consumer's proposal):** `sym_digest` as a `core_run_state` field + `fresh_given_int (d) (n)` + an explicit parameter on the OCaml `Cerb_fresh.digest` read — covers RUN-TIME minting only (program symbols would still carry the opaque read), changes the OCaml (the parameter must reach `Fork_renumber.fresh_symbol'` and every `fresh_*` site or the run's symbols get a different digest than the frontend's — a real divergence hazard), and touches `symbol.lem`/`core_run.lem`/`core_reduction.lem`/`driver.lem` bodies. D-A subsumes it with less surface.
**Timing.** cerberus-sl's P-call-F note says the digest is not needed for their current proxies; the consolidated note lists it first. Recommendation: charter E-A now (after seam hygiene, before or after the concurrency landing as §7 says) and D-A as the SAME arc's second slice, gated on one question to cerberus-sl relayed by the operator: "do you want `P.digest` now, or after your candidate (a) lands?" — D-A costs one lem line plus mechanical seam binders; its risk is entirely in the multi-TU pinning and the seam-binder churn, so it is cheap to do beside E-A and wasteful to do alone later.
