# Format: <row-key> <TRIAGED_CLASS> gcc=<exit> lean={<byte-set>} <rationale...>
# BY-FILE semantics (2026-08-30 audit follow-up + orchestrator ruling):
# an entry declares the file a divergence-class observer — the file is
# ALWAYS TRIAGED_<CLASS>, even when the two values happen to coincide
# (a layout coincidence is not agreement; counting it AGREE would
# inflate the metric and arm a flip-to-DISAGREE trap if either side's
# layout changes). Fields 3-4 are MACHINE-CHECKED PINS (lean = the
# expected-byte set exactly as the harness prints it, in every class;
# gcc = native exit byte under the §2.1 byte-stable execution recipe, in
# every class but TRIAGED_ADDR). On any drift from the pins the row
# surfaces as an unresolved DISAGREE (fatal, row named), forcing
# re-triage.
# TRIAGED_ADDR entries: <row-key> TRIAGED_ADDR src=<sha256> lean={<byte-set>}
# <rationale...>. An address observer's native value is the machine's
# process layout: six of these rows' gcc values moved when the project
# changed machine on 2026-11-24 (kernel and libc differ; identical under
# gcc 13.4 and 15.2), with no change to any program or to Lean's values.
# The entry therefore pins the PROGRAM (sha256 of the .c file: the
# reviewed claim is that this source observes an address) and Lean's
# value; gcc's value is printed by the lane, not compared: FOR THESE ROWS
# GCC IS NOT AN ORACLE (any deterministic native result passes). The row
# checks the program text, Lean's value, that gcc compiles it and that
# two native runs agree. A row's class may not change against the
# baseline without a deliberate re-record (fatal in --check-baseline).
# The gcc numbers in the rationales below are the first machine's, kept
# as history. [USER 2026-11-24] agreed to this form; design note §4. Classes +
# procedure: lean_frontend/docs/2026-08-30_gcc-second-oracle-design.md
# §4. FAIL-CLOSED both directions: unlisted DISAGREE is fatal; a
# listed file that no longer reaches the compare stage is fatal.
#
